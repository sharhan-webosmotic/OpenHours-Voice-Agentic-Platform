# FDA / IEC 62304 — required controls (checklist)

> Loaded by `/audit` when `compliance:` includes `fda` or `iec-62304`. Medical-device
> software lifecycle (IEC 62304) plus FDA premarket + quality-system expectations. This
> is a safety regime: the checklist is the process/artifact subset relevant to building
> the software. Clinical/regulatory submission is out of scope here.

## Software safety classification (IEC 62304)
- [ ] Software **safety class** assigned (A: no injury possible, B: non-serious injury,
  C: death or serious injury) and documented. Drives the rigor of every step below.

## Lifecycle processes
- [ ] **Software development plan** covering the lifecycle model.
- [ ] **Software requirements** specified and traceable to system/risk requirements.
- [ ] **Software architecture** documented (Class B/C).
- [ ] **Risk management** per ISO 14971: hazards identified, mitigations traced to code.
- [ ] **Verification**: unit/integration/system testing traced to requirements; results
  recorded.
- [ ] **Configuration management**: versioned, with change control and a build/release record.
- [ ] **Problem resolution**: a tracked process for defects and anomalies.
- [ ] **SOUP** (Software of Unknown Provenance): every third-party/OSS component is listed
  with version, and its known anomalies are assessed against the device's risk.

## Quality system & security
- [ ] Operating under a QMS (21 CFR 820 / ISO 13485) — documented, not ad hoc.
- [ ] **Cybersecurity** per FDA premarket guidance: threat model, SBOM, secure update path,
  vulnerability management.

## Verification (lean)
`/audit` checks:
- A software development plan, requirements trace matrix, and risk file are referenced
  in `AI_DOCS/` → CONCERNS if missing (Class B/C → FAIL).
- A **SBOM / SOUP list** exists enumerating dependencies with versions → FAIL if absent
  (a committed lockfile is the minimum; an explicit SOUP register is expected for B/C).
- Tests trace to requirements (test IDs map to requirement IDs) → CONCERNS if untraced.
- Dependency vulnerability scan in CI; secure-update mechanism documented.
- No unpinned dependency versions (shared with `development-rules.md` Rule 29/31).
