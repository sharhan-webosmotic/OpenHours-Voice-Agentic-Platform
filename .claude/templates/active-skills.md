# Active skills

> Two parts: (1) the **whitelist** of skills `/do` may dispatch in this project, and (2) the **Activation Map** that binds specialist skills to concrete, plan-derived trigger conditions so they fire automatically. Generated by `/do` Phase 0 (and `/plan`) from `stack.md` + the tech-spec dimensions. Re-derived by `change-request` when scope changes.
> The framework is a single flow — no `lean` vs `heavy`. Specialist skills (team-*, gate-enforcement, etc.) are dispatched by `/do` when project state demands them.

---

## Activation Map (auto-trigger)

> The mechanism behind "skills fire when needed". Each row is an armed specialist skill, the mechanical condition that arms it (evidence in the plan), the phase it fires in, and enforcement. `/do` evaluates these per task in the build loop and dispatches the skill instead of hand-rolling the work. BLOCKING rows are hard gates. `/do status` prints this table. `change-request` re-derives it on scope change.
>
> Status: `armed` (condition is true for this project) or `dormant` (condition false). Fill `Status` during planning from the evidence column.

| Skill | Trigger condition (evidence) | Fires in | Enforcement | Status |
|-------|------------------------------|----------|-------------|--------|
| ai-cost-guard | S22 has an LLM row, or a task imports an LLM SDK | before any LLM API code | BLOCKING | dormant |
| audit | `stack.md compliance` non-empty, or S20 rows exist | milestone close + pre-ship | required | dormant |
| audit-logs | sensitive endpoints in S20 / api-contract (auth) | per sensitive endpoint | required | dormant |
| data-migration | a task changes the DB schema (S7 / database-schema.md) | that task | required | dormant |
| i18n | S22 i18n = planned | locale task | required | dormant |
| caching-strategy | S22 Caching is a real pattern (not N/A) | cached-path task | recommended | dormant |
| error-handling (async/real-time resilience) | S22 Async work or Real-time transport is a real pattern (queue/worker/SSE/WebSocket/pipeline) | every async/queue/real-time task | BLOCKING (runtime-pattern fidelity gate in /build) | dormant |
| seo | S23 SEO row planned | public-page task | recommended | dormant |
| analytics | S23 analytics row planned | instrumentation task | recommended | dormant |
| error-handling | S22 error/observability planned (default yes) | setup + per feature | recommended | armed |
| accessibility-audit | frontend in stack | milestone close (UI) | required | dormant |
| design-discovery/tokens/screens | frontend in stack | Phase 0 planning | required | dormant |
| deployment-planning | non-POC, has a deploy target | before first ship | required | dormant |
| impeccable (vendored) | web UI surface in the plan (frontend in stack) AND `skills/impeccable/` installed | per UI task (polish, detect) + milestone close (harden, detect) + token changes (document) | advisory (dispatched by /do only) | dormant |

> Add a row whenever a milestone task carries a `needs:<skill>` tag (emitted by tech-specification / milestone-planning). Conditions MUST be mechanical (point at a spec row, a stack flag, or a file pattern) so /do evaluates them without guessing.
>
> **Impeccable mode mapping** (third-party vendored skill, upstream-owned, updated via `npx impeccable update`, never edited by ADF): `polish` = pre-visual-QA fix pass on UI tasks (fixes land BEFORE the DSC judgment), `harden` = milestone-close edge-case pass, `detect` = the mechanical anti-pattern lane (`npx impeccable detect --json` into `mavs/slop.json`, advisory), `document` = DESIGN.md refresh after `tokens.json` changes. `live` and `shape` stay dormant unless the operator asks. Naming disambiguation: an "impeccable audit" is a UI technical audit dispatched by /do. ADF's `/audit` remains the security and pre-ship audit, and the DSC checklist + `mavs/visual.json` remain the design verdict of record (impeccable is the fix engine, never the verdict).
